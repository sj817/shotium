# 渲染内存优化候选：Windows x64

本轮已实现并重建内存优化。真实样例中，简单页、Grid、综合页、4 倍和 8 倍卡片更快，普通卡片和噪声图等效；滤镜页仍有约 2% 的平均耗时差距，在预先固定的 2% 严格范围下未能证明等效。因此，**不能宣称所有场景性能均不退步**。

第三方截图缺少原始 HTML、脚本和进程统计范围，下面是本机仓库样例的测量。仓库 Grid 页也不是截图里的 24 张卡片页面。

## 最终版本内存

CLI 每个页面、每侧各 5 个独立进程，重复次序交替 AB/BA。普通页面连续 35 次截图，缩放卡片连续 6 次。下表为各进程 OS 高水位的中位数，单位 MiB；不是每请求采样峰值。完整范围和逐次记录见 `summary.json`、`memory.json`。

| 仓库样例 | 私有提交峰值：基线 → 当前 | 驻留工作集峰值：基线 → 当前 |
|---|---:|---:|
| 简单页，1280×720 | 29.0 → 27.2 | 50.7 → 48.4 |
| Grid，1280×720 | 30.1 → 26.1 | 51.7 → 47.5 |
| demo-card，800×450 | 77.3 → 31.0 | 99.3 → 53.9 |
| 综合页，1248×1320 | 41.1 → 38.3 | 63.6 → 60.8 |
| 滤镜页，1280×720 | 58.6 → 53.2 | 79.4 → 74.6 |
| 不易压缩的噪声图 | 27.1 → 27.1 | 46.7 → 46.8 |
| demo-card，4 倍 | 139.4 → 117.4 | 133.3 → 130.9 |
| demo-card，8 倍 | 515.7 → 441.5 | 394.4 → 382.5 |

卡片样例的私有提交峰值下降约 60%，工作集峰值下降约 46%；简单页改善明显小于卡片页，噪声图基本不变。8 倍卡片最终版本私有提交峰值下降约 74 MiB。前期版本曾测到约 88 MiB，本表只采用最终版本结果。

Windows 工作集表示驻留内存，private commit 不是 RSS。两个峰值可能发生在不同阶段，不能直接相减来归因。

## Node 宿主与引擎进程

普通 Node 子进程内没有 tsx loader；每侧每页面 3 个独立进程、每进程 35 次截图，不留存截图结果数组。

| 样例 | Node＋引擎工作集峰值：npm 0.12.2 → 当前 | 私有提交峰值：npm 0.12.2 → 当前 |
|---|---:|---:|
| 简单页 | 101.6 → 98.3 | 47.8 → 45.3 |
| Grid | 103.0 → 98.7 | 48.4 → 44.0 |
| demo-card | 149.1 → 106.2 | 93.4 → 49.6 |

这组 Node 测量进程在加载 Shotium 前已占约 53.7 MiB 工作集。最终简单页的 CLI 引擎进程约 48.4 MiB，而内嵌 Node 进程约 98.3 MiB。两者不是同一统计范围：CLI 一列不包含驱动程序自身的 Node 进程。Node 应用改成额外启动 CLI 时，宿主仍存在，不能将 48.4 MiB 当成整套应用总占用。

这说明应先区分宿主与渲染核心。现有 CLI/C ABI 已允许不依赖 Node 的调用程序使用同一引擎；单纯重写渲染核心不会自动消除调用侧的宿主开销。无法据此断言第三方的 95 MiB 一定包含 Node，仍需原测试脚本确认。

代码也确认了入口差别：`apps/typescript/package.json` 的 `bin.shotium` 指向 `dist/cli.js`，对应的 `src/cli.ts` 使用 Node shebang 并调用原生 addon。`npx @pixel.js/shotium` 因而仍包含 Node。这里测量的独立 CLI 是 `out/Shot/shotium.exe`。

## 修改与依据

1. **及时释放已退出页面的绘制记录。** `LocalFrameView::Dispose()` 清空该视图不再使用的 paint artifact 记录和子序列缓存。退出视图的 GC 对象原本仍持有引用计数的绘制记录；demo-card 连续截图时，Skia 缓存每次增长约 1.3 MiB，曾达到约 43.9 MiB，直到 GC 才回落。截图库已经取得的 cc display list 保留自己的引用，可以在页面退出后继续栅格化。
2. **PNG 条带直接编码。** 需要绘制外扩范围或抖动相位修正的多条带 PNG，直接借用工作线程临时 surface 的像素完成编码，移除复制到另一张完整／窗口位图的步骤。编码完成后才能复用该 surface。单条带和无需临时 surface 的路径、JPEG/WebP 保留原有方式；没有降低线程数、绘制精度或渲染功能。
3. **把失效缓存清理放进已有空闲阶段。** 绘制记录释放只会投递 Skia 图片缓存失效通知。V4 在原有空闲销毁任务中处理这些通知，避免下一次栅格化承担前一页面的清理工作。诊断确认，卡片编码后 Skia 缓存约 1.4 MiB，下次请求开始前已降到约 0.1 MiB；仍有引用的有效缓存不受这一步影响。
4. **PNG 行转换。** 不透明像素采用固定步长 RGB 通道转换，透明像素直接复制已经转换的 RGBA 行。上一轮已有的 64 KiB 初始压缩缓冲区优化仍保留。

没有增加 GC 频率，没有强制修剪工作集。当前 Skia discardable 配置走数量限制，不能将 `SetResourceCacheTotalByteLimit` 视为所有缓存的字节上限；本轮也没有用修改这个数字来代替处理对象存活时间。`SHOT_PROFILE=1` 配合 `SHOT_PROFILE_CACHE=1` 可查看分类缓存诊断，正式计时关闭 profiling。

## 性能结论与保留的失败结果

CLI 定向测试固定 body 2%、tail 5%，使用 99% 配对 bootstrap 区间。计时与内存采样分开，计时不包含输出哈希检查；首张图比较解码像素，之后每张检查稳定哈希。

- 最终普通卡片两次独立进程测试分别为 1500 对、3000 对，均为等效。后一轮 p50 比值 1.004、mean 比值 1.003。
- 最终滤镜页两轮分别为 1500 对、3000 对，均为未定。后一轮 p50 比值 1.020，99% 区间 [1.011, 1.027]；mean 比值 1.020，区间 [1.014, 1.027]，平均耗时从 26.232 ms 增至 26.769 ms，增加约 0.54 ms。这项仍未满足严格 2% 的等效证明。
- 最终简单页、Grid、综合页、4 倍和 8 倍卡片更快，噪声图等效。4/8 倍卡片均约快 3%。上述 8 个样例的基线和当前输出逐像素一致。
- V3 曾完成默认预算的完整 npm 矩阵：38 个更快、56 个等效、14 个未定。随后真实卡片的 1500 对复查出现 p50 约慢 4.9%、mean 约慢 3.9%，因此继续修正，未将 V3 视为最终版本。隔离复查存在进程／轮次变化，所有样本均保留。

最终 npm 矩阵覆盖全部 108 项。按首次 A/A 的 body +3.09%、tail +11.00% 冻结阈值重算后，**21 项更快、51 项等效、36 项未定、0 项明确变慢**。本轮新校准的原始判定是 21 项更快、62 项等效、25 项未定；本报告采用较严格的冻结结果，不使用新校准放宽标准。

V4 最低 100 对、上限 300 对，持续请求仍为 1000 对。短场景可能在达到默认 3 秒前触及上限；精度不足的项目保持未定。`--check` 返回 1：默认 improvement 门要求每个引擎场景都更快，等效也不接受。该门没有通过，“无明确退步”也不能证明全部场景等效。CLI 定向滤镜测试仍按原定 2% 范围单独判断，不能套用 npm 的较宽阈值。

完整逐项耗时、区间和样本数见 `timings.zh-CN.md`。初版和最终版完整矩阵、所有隔离实验及未定／退步结果均保留。

## 正确性与构建

最终 CLI、Node addon 和 C ABI DLL 均通过 `pnpm build:engine --jobs 2` 构建。初期默认 12 并发构建曾耗尽系统 commit，失败日志保留；没有将失败构建当作成功产物。

已通过：serve 100 项、网络 18 项（含在线 TLS 烟测）、渲染样例 92 个（69 精确、2 fuzzy、21 smoke）、编码 15 项、字体回退 3 项、Node 66 项、Node 入口 7 组、daemon 24 项、daemon 协议、长文章 135 项，以及 Python C ABI 的图片一致性、Unicode、错误和失败统计检查。

`pnpm accept --skip-build` 完成。相对现有 Chrome 参考图仍有约 1.524% 的像素差异，不是逐像素相同；本轮旧／新 CLI 的综合页输出逐像素一致。没有独立渲染基线 manifest，因此未运行可选 `pnpm render run`，像素证据来自 reftest 和成对输出。

V3 和最终 V4 的完整矩阵均完成了 108 组输出检查；两版各 108/108 组相对其 npm 基线逐像素一致。最终验证清单共 14 个命令，均返回 0；性能 improvement 门的返回 1 另行记录，不混入功能通过数。
